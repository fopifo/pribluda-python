Правила документации (2026-09-04)
======================================================================
Все аббревиатуры и специальные термины при каждом упоминании в каждом
разделе давать с расшифровкой на русском языке в скобках. Примеры:
- TP (истинно-положительные) — совпадение нашего сигнала с эталоном
- FP (ложно-положительные) — наш сигнал, которого нет в эталоне (шум)
- FN (ложно-отрицательные) — сигнал в эталоне, который мы пропустили
- ETA (оценочное время до завершения) — сколько осталось до конца операции
- LEN (длина серии) — количество повторов в серии робота
- A/B (сравнение двух вариантов) — эксперимент с двумя конфигурациями

В таблицах и повторяющихся метриках (например, "TP=49, FN=681, FP=36254")
расшифровки НЕ требуются — они должны быть даны при упоминании в разделе.

ГЛАВНАЯ ЦЕЛЬ ПРОЕКТА (зафиксировано 2026-09-07)
======================================================================
Наш детектор — главный источник торговых сигналов. Он должен ловить
роботов НЕ ХУЖЕ, А ЛУЧШЕ, чем aniscan.ru и T-Widgets:

1. Видеть ВСЕХ роботов, которых видят конкуренты
   (Recall наш ≥ Recall конкурентов)
2. Видеть их БЫСТРЕЕ (задержка детекции < задержки конкурентов).
   Если конкурент видит робота через 5 минут после старта, а мы —
   через 30 секунд — это наша победа, а не «норма».
3. Видеть с большей точностью (меньше ложных срабатываний, чем у них).

Aniscan.ru и T-Widgets — НЕ эталоны для соответствия, а КОНКУРЕНТЫ,
которых мы должны обогнать по скорости, полноте и точности.
Метрики против них нужны для измерения нашего ПРЕВОСХОДСТВА,
а не для «соответствия эталону».

Единственная правда — наш живой сигнал в бою и результат в сделке.

Следствия из этой цели:
- Любое улучшение Recall и сокращение задержки приоритетнее Precision.
- FN (пропущенные роботы) — это ВСЕГДА наш баг, а не «разное видение
  рынка». Если конкурент видит робота, а мы нет — чиним нас, не ищем
  оправданий.
- Живые метрики (задержка от первого удара) важнее офлайн-Recall.
- Тикеры, которые ловит aniscan/T-Widgets — это чек-лист того, кого
  мы ОБЯЗАНЫ ловить. Не поймали — разбираем как FN.

Приоритеты разработки (по убыванию):
1. Скорость (задержка детекции < 1 мин от первого удара)
2. Полнота (Recall ≥ Recall конкурентов)
3. Точность (Precision достаточная для уверенного входа)

разбивать длинные here-string на короткие pipe-команды.

своей строки.

Правила PowerShell для python -c (2026-09-05)
======================================================================
В python -c "..." ЗАПРЕЩЕНЫ f-string с экранированными кавычками \":
PowerShell закрывает строку на \" и ломает команду (ParserError,
MissingArrayIndexExpression). Повторялось многократно.
Внутри двойных кавычек PowerShell — только одинарные кавычки python,
print с аргументами через запятую, без f-string и срезов [:n].
Пример правильно:
python -c "import json;recs=[json.loads(l) for l in open('data/x.jsonl',encoding='utf-8')];[print(r.get('ticker'),r.get('period')) for r in recs]"
Сложная логика — в файл скрипта (tools/, research/), не в -c.

ПРАВИЛО ПОСЛЕДОВАТЕЛЬНОСТИ (2026-09-07, критично, навсегда)
======================================================================
Много раз было: после ПЕРВОЙ команды в хвосте ошибка, а помощник уже
расписал весь проект наперёд (планы «до/после закрытия», «вечером»,
«завтра»). Это непоследовательно и тратит время владельца.

Правило:
1. ОДИН шаг за раз. Дал ОДНУ команду (или один файл) — СТОП, жду хвост.
2. Проверил хвост — только тогда следующий шаг.
3. НЕ планировать наперёд блоки шагов («сначала А, потом Б, вечером В»).
   Владелец САМ пишет, когда продолжать и что дальше.
4. Если в хвосте ошибка — STOP. Чиним ТОЛЬКО её. Ничего больше не предлагаем.
5. Не давать несколько зависимых команд сразу. Независимые проверки
   (BOM + syntax) — максимум парой в одной команде.
6. Любое «что дальше» решает владелец, не помощник.

Это правило выше любых планов и дедлайнов.

Идея (код владельца, дословно): если qty серии — один из самых частых
объёмов у тикера за день (обычный рыночный размер, не редкость),
grid_lock НЕ должен клеить пропуски через кратные k·base — только

```python
"""
Фрагмент для detectors/interval_robot.py — не отдельный файл, вставить
внутрь класса, рядом с существующей grid_lock-логикой.

ПРОБЛЕМА (SBER-кейс, 09-08): grid_lock принимает почти любой зазор как
"k пропущенных ударов" базового периода — на ликвидных тикерах, где
qty=10 (или другой круглый размер) — обычный рыночный размер, а не
редкость, это клеит случайные сделки в фальшивую "серию".

ИДЕЯ: если qty серии — один из самых частых объёмов у этого тикера за
день (не редкость), grid_lock для этой серии отключается — разрешено
только точное совпадение интервала (без "прощения" пропусков через
kʹbase). Требует внешнего словаря частых qty по тикеру за день,
считается заранее (до старта детекторов на день), не на лету.
"""

# Готовится один раз в начале дня (в run/main), передаётся в детектор
# при создании: noisy_qty_by_ticker: dict[str, set[int]]
# Порог "частый объём": qty встречается в >= NOISY_QTY_SHARE от всех
# сделок этого тикера за день.
NOISY_QTY_SHARE = 0.03  # 3% всех сделок дня одним и тем же qty — уже подозрительно часто


def compute_noisy_qty(day_trades_by_ticker: dict) -> dict:
    """day_trades_by_ticker: {ticker: [qty, qty, ...]} — все объёмы
    сделок тикера за день (до фильтра min_qty). Возвращает
    {ticker: set(qty)} — объёмы, которые считаются "шумовыми"
    (слишком частый обычный рыночный размер, не признак робота)."""
    from collections import Counter
    result = {}
    for ticker, qtys in day_trades_by_ticker.items():
        if not qtys:
            continue
        total = len(qtys)
        counts = Counter(qtys)
        noisy = {q for q, c in counts.items() if c / total >= NOISY_QTY_SHARE}
        result[ticker] = noisy
    return result


# В самом детекторе — при попытке grid_lock-склейки (k > 1, не точный
# интервал) добавить проверку:
#
#   if k > 1 and qty in self.noisy_qty:
#       return None  # шумовой объём — только точное совпадение, без grid_lock
#
# self.noisy_qty — передаётся в __init__ детектора как параметр
# (noisy_qty_by_ticker.get(symbol, set())), не считается внутри самого
# детектора — иначе пришлось бы гонять по всей ленте дня до старта.
