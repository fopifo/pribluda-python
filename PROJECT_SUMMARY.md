# Приблуда на python

Скринер торговых роботов (алгоритмов) на Московской бирже (MOEX).
Заказчик — трейдер-скальпер без опыта программирования, торгует на MOEX.
Цель: одним из первых находить работающие алгоритмы в стакане/ленте
сделок и заходить в сделку вслед за ними.

Данные — API брокера Алор. Есть два режима работы:
  - исторический (батч) — save_trades.py скачивает ленту сделок за
    прошлый торговый день, run_detectors.py прогоняет её через
    детекторы целиком. Нужен для тестирования порогов и логики.
  - живой (WebSocket) — live_screener.py подключается к потоку сделок
    в реальном времени (AllTradesGetAndSubscribe), сигналы появляются
    сразу, без ожидания конца дня. Это основной рабочий режим —
    трейдеру критична скорость обнаружения, а не анализ прошлого.

## Идея детекции

Робот = серия сделок одной стороны (buy/sell), одного тикера,
повторяющаяся через устойчивый интервал времени, с объёмом лота из
небольшого набора вариантов (робот может чередовать 1-2 значения объёма,
чтобы маскироваться, например 45/46 лотов). Объём робота может быть как
крупным, так и мелким — важна устойчивость периода, а не размер сделки.
Фильтр по объёму (min_qty) — низкий пол (процентиль дневного объёма),
отсекающий только пыль, не потолок.

Два семейства пресетов интервала:
  - fast (2-30 сек) — аналог классической "трёхсекундки"
  - slow (60-600 сек) — "прокиды", крупные редкие удары

И два режима строгости:
  - loose — широкий поиск (есть в коде, но по умолчанию выключен —
    источник ложных сигналов, "похожих на робота")
  - strict — требует устойчивого повторяющегося периода
    (interval_tolerance) и постоянного объёма — включён по умолчанию,
    точность важнее количества

min_repeats = 2 везде: даже короткая серия — валидный сигнал, счётчик
повторов (LEN) сам несёт информацию о надёжности, фильтровать на уровне
детектора не нужно — трейдер решает сам, глядя на счётчик. Роботов
включают и выключают много раз за день — это нормально и ожидаемо.

Референс по UI/логике — сторонний скринер (Quik): колонки
TICKER/QTY/INT/LAST/NEXT/LEN, прогноз следующего удара (NEXT), пометка
"черепом" при пропуске ожидаемого удара, удаление после второго пропуска.
В нашем коде это реализовано как watchdog: check_overdue() проверяет
активные серии по таймеру (раз в 1 сек в живом режиме) и предупреждает
о просрочке ДО того, как придёт следующая сделка (которой может не быть).

## Статус на сейчас

- Детектор IntervalRobotDetector: гибкий интервал, чередование объёма,
  оптимизирован под низкий порог объёма (индекс по qty, предохранитель
  от неограниченного роста активных серий), метод check_overdue для
  живого мониторинга с ранним предупреждением о просрочке.
- Живой режим (live_screener.py) реализован: подключение к WebSocket
  Алора, автопереподключение каждые ~20 мин (access-token живёт 30 мин),
  сторож с интервалом проверки 1 сек, лог пишется в
  output/live_signals_<дата>.txt.
- Тесты (tests/test_interval_robot.py) написаны и проверены — 10/10
  проходят.
- Инструмент анализа живых логов (tools/analyze_live_log.py) — считает
  статистику по тикерам (сигналов, средний/макс LEN, предупреждения).
- Отслеживаем 11 тикеров: SBER, FLOT, HEAD, PIKK, MAGN, FEES, ASTR,
  CHMF, PHOR, RENI, TGKA.
- Проект структурирован по папкам: detectors/ (ядро), tools/
  (вспомогательные скрипты — статистика, разведка API, анализ логов),
  tests/, data/ (исторические ленты), output/ (результаты и живые логи),
  dumps/ (снимки проекта для делегирования DeepSeek).
- Ещё не реализовано: UI/дашборд с обратным отсчётом и счётчиком LEN
  (сейчас всё в виде текстового лога), группировка "двойных роботов",
  паттерны "кэшбек"/"разнолот"/"змейка" (пока только периодичность).
- Первый живой запуск (live_screener.py) запланирован на завтра, при
  открытии торгов.
